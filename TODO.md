# WALDO remaining work

This is the prioritized product backlog after the working index, ingestion,
training, model-export, and calibrated-quantization slices. Detailed completed
history remains in [the roadmap](docs/ROADMAP.md); this file is intentionally
about unfinished work.

## 1. Index maintenance

- Add explicit corpus-removal contribution overlays with optional guarded
  lookaside object deletion.
- Design non-text and multimodal ingestion as a separate bounded phase.

## 2. Distribution

- Add `waldo model push <name> <huggingface-target>`.
- Reuse the verified export pipeline and support an explicitly selected
  Hugging Face, MLX, GGUF, or Ollama representation.
- Carry `--quant` and index-backed `--calibration` into GGUF/Ollama pushes.
- Authenticate through standard Hugging Face credentials and publish one
  reviewable commit without silently overwriting unrelated remote files.

## 3. Model lineage and tuning

- Add explicit model fork and parent-lineage operations.
- Broaden Hugging Face tokenizer and architecture compatibility beyond the
  initial Llama plus OpenWALDO byte-tokenizer profile.
- Define supervised fine-tuning records, objectives, evaluations, and BOM
  evidence.
- Pin chat templates rather than inferring instruction behavior.
- Add preference training only after the SFT and evaluation contracts are
  stable.

## 4. Compiled training data and corpus mixtures

Canonical Parquet must remain tokenizer-neutral. Training should consume a
derived, reproducible compiled view so tokenizer choice, corpus composition,
and sampling behavior are reviewable run inputs rather than hidden backend
behavior. Implement this before relying on corpus-sensitive sparse routing.

- Implement the compiled training view described in
  `docs/INGESTION-DESIGN.md`. Its identity must pin the OpenWALDO BOM, exact
  tokenizer artifacts and implementation revision, normalization and special
  tokens, document/EOS boundaries, context length, packing, masking, split,
  and shuffle algorithms.
- Replace the current byte-token-only training handoff with token arrays and
  document/sample indexes generated by that view. Keep the manifest's
  `cl100k_base` counts explicitly informational; never substitute them for the
  selected model tokenizer's exact counts.
- Produce deterministic tokenizer diagnostics before training, partitioned by
  corpus, source, language, and declared data class: token and sequence-length
  distributions, bytes per token, fallback/unknown behavior, truncation, and
  special-token collisions. Make the report a pinned run input and fail
  preflight on incompatible tokenizer artifacts or invalid boundaries.
- Preserve corpus manifest path, source identity, language, logical record
  kind, and approved quality/domain labels through compilation and the worker
  protocol. Training backends need these labels for mixture accounting and
  router telemetry, but fetchers must remain acquisition-only.
- Add an immutable mixture recipe for each training stage. It must express
  per-corpus weights or token budgets, deterministic sampling, curriculum
  phases, and named masking policy. Record planned and observed token totals by
  corpus and phase in the run BOM/observation.
- Define exact and near-duplicate policy across all corpora selected by a run.
  Ingestion's license-aware record retention remains provenance-preserving;
  the compiled view must make any cross-corpus suppression or reweighting
  explicit and reproducible.

Acceptance requires rebuilding byte-identical compiled-view indexes from the
same BOM and recipe, detecting any tokenizer/configuration change, reconciling
per-corpus token totals, and proving held-out records never enter a training
sample.

## 5. Portable sparse MoE architecture and routing

WALDO should define a portable sparse-MoE contract, not prescribe SMEU or any
other research-specific router. The default should be a conservative,
general-purpose top-k router. A backend or downstream integrator must be able
to provide another router without changing corpus formats or bypassing model
and run provenance.

- Extend the model architecture with a versioned sparse-MoE block definition:
  expert count, active top-k, expert intermediate size, shared-expert policy,
  MoE layer placement, capacity/overflow policy, router precision, and expert
  and context parallelism requirements. Update parameter, memory, checkpoint,
  and communication forecasts accordingly.
- Define a portable router selection containing an immutable name, revision,
  and canonical configuration. Provide a generic top-k default with explicit
  load-balancing auxiliary loss and router z-loss settings. Keep SMEU, learned
  bias updates, and other algorithms optional named implementations rather
  than WALDO defaults.
- Add a router capability/registration boundary to training adapters. Custom
  routers must declare supported configuration, metrics, checkpoint state,
  precision, and parallelism. Backend resolution must fail before a run is
  created when it cannot honor every pinned MoE/router field; it must never
  silently replace a router or balancing algorithm.
- Extend worker/checkpoint/export contracts for expert weights, router weights
  and state, and expert-parallel layouts while retaining portable logical
  tensor names. Resume must reproduce routing state and deterministic data
  order exactly.
- Implement sparse execution in the distributed PyTorch/TorchTitan adapter,
  including expert parallelism. Keep dense MLX and PyTorch behavior unchanged
  until those adapters explicitly advertise sparse-MoE support.
- Build and check in a sparse-MoE model compose that uses the generic router.
  Start with a small, CPU/testable configuration that proves compose parsing,
  forecasts, training, checkpoint/resume, and export; add a separately named
  distributed reference compose with realistic expert-parallel settings once
  the TorchTitan path is qualified.

Acceptance requires a third-party router implementation to run through the
same compose, preflight, run BOM, checkpoint, observation, and export lifecycle
as the generic router without modifying WALDO's canonical corpus schema.

## 6. Router observability and data feedback

Sparse training must not use aggregate loss as its only health signal. Router
measurements are durable run evidence and should be attributable to the corpus
mixture that produced them.

- Record per-layer and per-expert routed-token counts, load mean/min/max,
  max-to-min imbalance ratio, coefficient of variation, routing entropy, dead
  experts, capacity overflow or dropped tokens, router probability/logit
  summaries, auxiliary loss, and z-loss.
- Aggregate the same measurements by training phase and the compiled view's
  corpus/source/language/data-class labels. This allows out-of-distribution
  or underrepresented data to be identified without exposing those labels to
  the router as supervision.
- Define portable progress-event and terminal-observation schemas for router
  metrics. Preserve backend-specific metrics under a namespaced extension
  without weakening the required common measurements.
- Add configurable early-run warning and abort thresholds for expert collapse,
  overflow, non-finite router values, and prolonged imbalance. Defaults should
  detect dead or runaway experts without demanding perfectly uniform routing,
  since useful specialization requires some variation.
- Add deterministic tokenizer, dense-baseline, generic-router, and custom-router
  ablation fixtures so a team can narrow failures before committing a large
  run. Document a restart/continue decision record that pins the evidence and
  configuration change.

Acceptance requires tests where ordinary loss remains finite while synthetic
router collapse is detected, persisted, attributed to the responsible data
slice, and surfaced before the run's configured early-stop boundary.

- PyTorch generation.
- A TensorFlow training adapter.
- Multi-node TorchTitan rendezvous, scheduling, and orchestration.
- Broader cluster-management integrations.

These are valuable extensions, but they are not blockers for a dependable
first release built around MLX, PyTorch, and single-node TorchTitan training.
